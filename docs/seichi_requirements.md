# 聖地巡礼・地域周遊Webアプリ 要件定義

更新日：2026年9月26日
状態：開発用仕様。外部APIの対象地域での動作、費用、利用条件は実際に検証して確定する。

## 1. 目的と提供価値

好きなアニメ・ドラマ・映画のモデル地やロケ地をきっかけに、周辺の食・店・文化施設にも立ち寄れる周遊コースを提案する。ユーザーは行きたい聖地を選び、周遊に使える時間の長さを指定する。アプリは訪問順、寄り道候補、訪問地点間の移動時間の目安と経路確認リンクを示す。

主な利用者は、行きたい聖地はあるが、周辺に何があるか、公共交通と徒歩でどの順番に巡ればよいか調べる負担が大きい人。地域にとっては、聖地への来訪を地域内の飲食・買い物・体験につなぐ機会を作る。ただし、コース表示だけで来訪や消費が増えたとは判断しない。

**このサービスは訪問地点を巡る順番の下書きを提供する。最初の地点までと最後の地点からの移動、乗車便、運行状況、臨時休業、予約成立は計画対象外または未確定である。** 出発前に各地点間のGoogleマップと施設・交通機関の公式情報を確認してもらう。

## 2. 対応範囲

| 項目 | 仕様 |
| --- | --- |
| 提供形式 | スマートフォン優先の日本語Webアプリ |
| 作品 | DBで公開済みのアニメ・ドラマ・映画。1回のコースで1作品を選択 |
| 地域 | 地点と移動経路を確認して公開した国内地域。未整備地域は対応外と表示 |
| 聖地 | 作品のモデル地またはロケ地であり、作品との関係と出典を確認した地点 |
| 寄り道 | 聖地周辺の飲食、地元商品、文化・体験スポット。作品との関係がない場所は聖地と区別 |
| 移動 | 徒歩・電車・バス。経路APIが別の移動手段を返した場合は採用しない |
| 訪問地点 | ユーザーが選ぶ必須聖地は1～3件。寄り道を含むコースは最大5件。上限は処理負荷と操作性を確認して調整 |
| 計画対象 | 選んだ聖地と寄り道の訪問順、および隣り合う訪問地点間の移動。最初の地点までと最後の地点からの移動は含めない |
| 費用 | 判明している訪問地点間の交通費・施設料金・飲食や体験の参考価格を内訳として表示。不明は不明と表示。計画対象外の移動費は含めない |
| アカウント | コースを見るための登録は不要。コースの長期保存、予約、決済、運休時の自動再計画は提供範囲外 |

掲載数を固定の目標件数にせず、出典と現地での利用可能性を確認できた作品・地域から公開する。対応していない作品や地域について、AIが地点を即興で補完しない。

## 3. ユーザーの操作と画面

| 画面 | 操作 | 表示 |
| --- | --- | --- |
| ① 作品・地域 | 対応作品を探して選ぶ。複数地域に聖地がある作品は対応地域を選ぶ | 対応作品・地域と対応外の案内 |
| ② 聖地マップ | 行きたい聖地を1～3件選ぶ | 地点名、ピン、作品との関係、根拠URL、滞在目安、立入・撮影上の注意 |
| ③ 条件入力 | 訪問日、周遊に使える時間の長さ、必要なら各聖地の滞在時間を設定。登録済み休業日がある地点はこの段階で見直す | 入力条件、休業する地点名、次に聖地を巡れる日付の候補、結果が概算になること |
| ④ コース | 提案を確認し、営業日として登録されている寄り道を追加・削除して再計算する | 訪問順、各滞在・訪問地点間の移動時間、現地での周遊時間の目安、地域スポットの理由、費用、訪問地点間のGoogleマップリンク、要確認事項 |

操作順は「作品・地域 → 聖地 → 条件・既知の休業日確認 → 基本コース → 寄り道の追加・削除 → コース確認」。選択した必須聖地をアプリが勝手に削除しない。登録済み休業日に当たる聖地・選択済み寄り道がある場合はコース作成前に地点名を示し、日付変更か寄り道削除を促す。条件に合う案を出せない場合は、理由と変更可能な条件を示す。

## 4. 入力と出力の意味

| 入力 | 必須 | 用途 |
| --- | --- | --- |
| 作品・公開済み地域 | 必須 | 対応データの特定 |
| 行きたい聖地 | 必須、1～3件 | 全てのコース候補に含める |
| 訪問日 | 必須 | 通常の営業日・既知の休業日と経路APIの対応期間を確認 |
| 周遊に使える時間の長さ | 必須 | 訪問地点での滞在、地点間の移動、余裕時間の概算と比較する。帰りの便や帰着時刻の判定には使わない |
| 各聖地の滞在時間 | 初期値あり | ユーザーが変更できる。勝手に短縮しない |
| 寄り道 | 任意 | 追加・削除するたびに訪問順と移動時間を再計算 |

日本時間で扱う。予算、好み、自由文は必須入力としない。入力していない好みをAIが推測したかのように説明しない。

**現地での周遊時間の目安**は、各訪問地点の滞在時間、隣り合う訪問地点間で取得できた移動時間、アプリが別に設けた余裕時間の合計。最初の地点までと最後の地点からの移動は計算しない。取得した経路時間に含まれる待ち時間を二重計上しない。検索条件や便により結果が変わるため、到着・終了時刻や帰着は判定しない。将来、必要なら駅などの出発・終了地点を任意で指定できる機能を検討する。

## 5. コースの表示と判定

| 表示 | 内容 |
| --- | --- |
| 訪問順 | 必須聖地・寄り道だけを並べる。作品に関係する聖地と地域の寄り道を視覚的に区別 |
| 地点 | 滞在時間の目安、通常営業時間、最終入場、料金、予約要否、公式URL、出典と確認日 |
| 移動区間 | 隣り合う訪問地点間だけに、徒歩／電車・バスの種別、移動時間・徒歩距離の目安、両地点を指定したGoogleマップ経路リンクを表示 |
| コース全体 | 滞在・訪問地点間の移動・余裕時間の内訳、「現地での周遊時間の目安」、指定した周遊時間との差、判定とその根拠。最初と最後の地点への移動は含まないと明記 |
| 費用 | 訪問地点間の交通費の取得できた範囲、施設料金、飲食・体験の参考価格を分けて表示。未取得項目は0円扱いしない。計画対象外の移動費は除く |
| 注意 | 当日の便、運休、臨時休業、予約を確認する案内と公式情報へのリンク |

判定は次の4つに分ける。

- **目安では収まる**：取得できた訪問地点間の経路をもとにした周遊時間の概算が、指定した時間内に入る。帰りの便や帰着時刻は判定しない。
- **要確認**：経路・営業時間・入場・予約・費用の重要な情報が足りない、または概算の余裕が少ない。理由を個別に示す。
- **目安でも収まらない**：周遊時間の概算が指定時間を超える。休業日は時間超過と混同しない。
- **計算できない**：経路APIの障害・データ不足・対応期間外・探索上限。訪問不可能とは区別する。

営業時間については、登録済みの曜日別営業時間、昼休み、既知の例外日を使う。訪問時刻を指定しないため、訪問日が営業日でもその時間帯に営業中とは断定しない。最終入場や時間帯による制約は「要確認」として示す。屋外地点は「営業時間なし」と「不明」を区別する。

登録済みの定休日・例外休業日はコース作成前に判定する。必須聖地が休業する日はコース作成を止め、地点名と次に全件を巡れる日付の候補を示す。選択済み寄り道が休業する日は、条件画面でその寄り道を外すか日付を変更できる。コース画面では休業する寄り道を追加不可として理由を表示する。未登録の臨時休業までは保証できないため、公式情報での再確認を促す。

Googleマップを開くリンクは、隣り合う訪問地点間だけに設け、両地点と徒歩または公共交通モードを設定する。地点だけを開くリンクも用意する。Maps URLsは訪問日時をリンクへ引き継げないため、画面上で訪問日を見せ、「Googleマップ側で日時を指定して確認」と案内する。外部地図の結果はアプリ内の概算と異なり得る。

## 6. コース作成の処理

1. 入力の形式、公開地域、地点数、訪問日と周遊に使える時間の長さを検証し、選択地点の登録済み休業日を先に確認する。該当時はコースを作らず変更を促す。
2. DBから選択した聖地、入口座標、地域の寄り道候補、滞在時間、営業条件、料金、出典を取得する。
3. 必須聖地の訪問順を候補化する。3件なら最大6通り。移動距離や同じ地域内の近さで明らかに遠回りな案を先に除く。
4. 各候補について、**隣り合う訪問地点ごと**にGoogle Routes APIで徒歩または公共交通の経路を調べる。最初の地点までと最後の地点からの移動は検索しない。選んだ訪問日の検索可能期間、交通データの有無、許可した移動手段を確認する。時刻を指定しない段階では、経路APIに必要な代表時刻を検索条件として用いる場合でも便や発着時刻を確定表示せず、仮定と概算であることを明示する。
5. 滞在・訪問地点間の移動・別途設定する余裕時間を合算し、指定した周遊時間との差、徒歩負担、データ不足を判定する。訪問時刻が必要な営業時間・最終入場は要確認とする。登録済み休業日は時間超過判定に混ぜない。
6. 経路沿い、駅・バス停周辺、必須聖地周辺の登録済み寄り道を絞り、追加時に変化する訪問地点間の区間を検索し直す。寄り道後も必須聖地を全て含める。
7. 計算した候補をAIへ渡し、訪問順と地域の寄り道のおすすめを選ぶ。サーバーはAIの返した候補ID、地点、判定理由を検査し、検査済みの時間の目安・費用と組み合わせて返す。
8. ユーザーが寄り道を追加・削除したら再計算する。成立しない場合は黙って削除せず、超過や不明の理由を示す。

API呼び出し回数・処理時間の上限を設定する。上限で探索を終えた場合は「今回調べた候補では見つかりませんでした」と表示し、地域全体に可能な経路がないとは断定しない。APIの結果に対象外の移動手段しかない場合や主要区間の経路が得られない場合は、そのコースを「公共交通で巡れる」と評価しない。

## 7. AIが実行すること

AI APIには、登録済み地点と、サーバーが計算した候補の構造化データを渡す。AIは次を行う。

1. 必須聖地を全て含む候補から、移動負担、時間の余裕、寄り道の地域性を比較して提案順を決める。
2. 「聖地の近くで地元料理を食べられる」「途中の乗換地点から立ち寄りやすい」など、登録済みの根拠と計算結果に即した理由を短く説明する。
3. 必須聖地を残したまま、寄り道を追加した候補や寄り道なしの候補の違いを説明する。

AIの出力は候補ID、寄り道ID、推薦理由などの決められた形式に限定する。AIに新しい聖地、店舗、作品との関係、時刻、運賃、営業時間、料金を創作させない。AIが選んだ候補の全地点がDBに存在し、ユーザーの必須聖地を全て含むかをサーバー側で検査する。AIの応答が不正・時間切れの場合は、検査済み候補を移動負担などの固定基準で並べて表示する。

AIが役割を持つのは**コース候補の選択と寄り道の推薦**である。物理的な移動可否の判定をAIの文章だけで済ませない。

## 8. データの取得・更新

| データ | 取得・管理方法 |
| --- | --- |
| 作品と聖地の関係 | 作品公式、自治体、観光協会、施設公式、確認可能な制作資料などを調査し、関係の説明と根拠URLを独自DBへ登録 |
| 聖地・施設の位置 | 入口・集合場所を確認して座標と説明を登録。施設中心座標と区別 |
| 地域スポット | 自治体・観光協会・施設情報や現地確認から選び、地元事業者か、地域産品・文化との関係があるかを別々に記録 |
| 通常営業時間・料金・予約 | 施設公式を優先して確認。出典・確認日・不明状態・既知の例外を記録 |
| 移動時間 | コース作成時に経路APIから取得し、画面では目安として表示。応答の保存は提供元の利用条件に従う |
| 画像 | 権利を確認した画像のみ掲載。なくてもコースを利用できるようにする |

運営者がCSVで地点を登録し、公開前に作品との関係、重複、座標、立入可否、リンクを確認する。閉店・立入禁止・誤登録を把握した地点は公開停止できるようにする。調査済みでも日本国内の聖地を網羅したとは表示しない。

外部の聖地マップやサービスから一括取得する場合は、対象項目と利用条件、DB保存、再公開、更新方法を確認する。推しワク・AnitabiなどのスクレイピングやAPIが利用可能であることを開発の前提にはしない。公式サイトに載る文章・画像を転載できるとは限らないため、説明文は確認した事実をもとに独自に書く。

## 9. API構成と採用条件

| 用途 | API・サービス | 使い方・注意 |
| --- | --- | --- |
| 作品・地点・営業情報 | Supabase／PostgreSQLの独自DB | 公開済みの情報のみユーザーに返す。更新は運営者に限定 |
| 地図と地点ピン | Google Maps JavaScript API | 地図上で聖地と寄り道を区別して表示。地図用キーの利用元・利用APIを制限 |
| 区間移動 | Google Routes API | 隣り合う訪問地点間に限り、徒歩・公共交通の移動時間の目安を取得。対象地域と日に経路が返るか実測で確認 |
| 地図で当日の経路を確認 | Google Maps URLs | 隣り合う訪問地点間の両地点と移動手段をリンクへ入れる。Googleマップで日時を指定して確認してもらう |
| おすすめコースの選択 | Gemini API（Interactions API） | 計算済み候補のIDを選び、根拠に基づく理由を返す。キーはサーバー側で保管 |
| Webアプリ内API | `GET /api/works`、`GET /api/spots`、`POST /api/itinerary` | 条件入力を受け、公開データ・コース候補・概算・要確認理由を返す |

### 9.1 画面別API仕様と実装状況

| 場面 | 使用するAPI・データ | 実行すること | 状況 |
| --- | --- | --- | --- |
| ① 作品を検索 | `GET /api/anilist/search` → AniList、`GET /api/anilist/match` → Supabase | AniList候補IDを独自DBと照合。未登録・聖地未確認作品は対応外と表示 | 実装済み。`GET /api/works` への統合は未実装 |
| ② 聖地を地図で選ぶ | `GET /api/anilist/match` → Supabase、地図表示 | 確認済み聖地の座標と根拠を表示。地図APIは聖地の取得元にしない | 現在はOpenStreetMap埋込。`GET /api/spots` とGoogle Maps JavaScript APIは未実装 |
| ③ 日付・地点・周遊時間を入力 | `POST /api/itinerary` | 1～3聖地、日付、周遊時間、所属・登録済み休業日をサーバーで検証 | 実装済み。開始・終了地点や帰着希望時刻は入力しない |
| ④ 移動を調べる | Google Routes API `computeRoutes`、Google Maps URLs | 選択地点同士の隣接区間だけ徒歩・公共交通を照会し、概算とリンクを表示 | Routesキー設定時に実行。未設定・取得不能時は出典付き登録済み区間があれば代用し明示 |
| ⑤ コース候補を作る | `POST /api/itinerary` → Supabase＋Routes API | 訪問順を比較し、滞在・地点間移動・余裕と周遊時間を判定 | 基本コースを実装。乗車便・時間帯別営業時間・帰着は判定しない |
| ⑥ おすすめを選ぶ | Gemini Interactions API | 計算済み候補IDと理由を返す。サーバーでID検査、障害時は固定基準に戻す | Geminiキー設定時に実行 |
| ⑦ 寄り道を追加・削除 | `POST /api/itinerary` 再実行 → Routes API・Gemini | 寄り道を含む隣接区間を再計算し必須聖地を残す | 寄り道データ・UIは未実装 |
| ⑧ 結果から地図を開く | Google Maps URLs | 地点・区間をGoogleマップで開く。同じ便が表示される保証はない | 実装済み。Maps URLsにAPIキーは不要 |

`POST /api/itinerary` の入力は `{ workId, region, spotIds, visitDate, availableMinutes }`。レスポンスは `{ course, recommendation, source, notices }` または `{ error }`。サーバーは地点の座標・移動時間をDBから再取得し、クライアントの値を信用しない。`GOOGLE_ROUTES_API_KEY` と `GEMINI_API_KEY` はサーバー専用とする。現在の連打制限はプロセス内の簡易実装（1分5回）であり、公開前に共有ストアを使う制限とGoogle Cloud／Gemini側の課金・利用上限を設定する。

Routesの公共交通は代表時刻で検索した概算。対応期間外・地方路線欠落・徒歩経路の歩道情報不足を想定し、実際の乗車・帰着は保証しない。Geminiは計算済み候補の選択のみを担当する。

Google Routesの公共交通経路は途中経由地を指定できないため、コース全体を一括検索せず区間ごとに調べる。交通運賃は全区間で取得できない場合があり、未取得は「不明」とする。検索できる日付の範囲と地方路線の収録はAPIと対象地域で確認する。APIレスポンスを無条件に恒久保存しない。Google Routes由来の結果を地図に重ねる場合はGoogleの地図表示・帰属条件に従う。

RapidAPI版NAVITIME Route(totalnavi)は経路の概算調査に使えるが、電車・バスの時刻表オプションをAPIマーケットで利用できない。特に地方バスの経路を必要とするコースの主たるデータ源として採用しない。Google Routesで必要な区間が取得できない場合は、その区間を未確認として扱うか、対象地域に適した利用可能な交通データを別途調達する。ユーザーに架空の便を提示して穴埋めしない。

**確認した公式資料**： [Google Routes・公共交通](https://developers.google.com/maps/documentation/routes/transit-route)、[Google Routesの利用条件](https://developers.google.com/maps/documentation/routes/policies)、[Maps JavaScript API](https://developers.google.com/maps/documentation/javascript/overview)、[Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)、[Gemini Interactions API](https://ai.google.dev/gemini-api/docs/interactions-overview)。2026年9月26日に「君の名は。」の飛騨市2地点で実リクエストを行い、Google Routesの徒歩8分とGeminiの候補選択を画面まで確認した。公共交通は別途東京駅―新宿駅を照会したが経路0件であり、利用可能性は未確認。公開前に対象地域の公共交通、キー制限、課金上限、共有型のレート制限を検証する。

## 10. 技術とデータ構造

画面・サーバーはNext.js、React、TypeScript、UIはTailwind CSS、DBはSupabase／PostgreSQLを採用する。入力と外部応答はスキーマで検証する。ルート探索・AI呼び出し・外部APIキーはサーバー側で管理し、連打制限と利用量の上限を設ける。

| テーブル | 主な項目 |
| --- | --- |
| 作品 | ID、作品名、種別、検索用別名、公開状態 |
| 地域 | ID、名称、座標、対応作品。駅・地点は将来の任意指定機能に備えて保持できるが、現行コース入力には使わない |
| スポット | ID、名称、カテゴリ、座標、入口、滞在目安、公式URL、公開状態 |
| 作品と聖地の関係 | 作品ID、スポットID、関係説明、根拠URL、確認状態 |
| 営業・料金 | 営業時間帯、定休日、既知の例外、最終入場、入場料、予約要否、参考価格 |
| 地域性 | 地元事業者か、地域の産品・文化との関係、根拠 |
| 情報源 | 項目、URL、確認日、担当、転載・保存条件 |

作品とスポットは多対多にする。未確認項目は空欄を0や「営業中」に変換しない。公開読取と運営者の更新権限を分け、個人の行動履歴は必要な範囲に絞って扱う。

## 11. 完成条件と検証

- 必須聖地を全て含めた訪問順を提示できる。最初と最後の地点への移動は含めず、駅の指定を求めない。
- 隣り合う訪問地点間だけに移動時間の目安と、**その区間の両地点を指定した**Googleマップリンクを表示できる。
- 徒歩・電車・バス以外を公共交通コースとして採用しない。主要区間を取得できないときは理由を表示する。
- 寄り道の追加・削除で訪問順、移動時間、費用の概算、判定を更新する。必須聖地を自動で削除しない。
- 既知の休業日、営業時間不明、予約要、運賃不明、経路API障害を区別できる。
- 登録済み休業日がある聖地・寄り道を含むコースは作成前に止め、変更可能な日付または寄り道削除を案内できる。休業中の寄り道は追加できない。
- AIが存在しない地点や便を返しても表示しない。AI障害でも計算済みコースを見られる。
- コース画面に「現地での周遊時間の目安」と対象範囲を明記し、便・臨時休業・予約の要確認を示す。帰りの便や帰着時刻を判定したと誤認させない。
- 現地で経路・入口・営業時間と概算との差を試し、利用者には「旅の候補を決めやすくなったか」「寄り道したか」を確認する。

開発は、①対象地域の経路取得と入口・地点データの確認、②作品と聖地の登録、③基本コースと区間リンク、④寄り道の再計算、⑤AIの選択、⑥現地試験の順で進める。地域への効果は、利用者の寄り道追加・実際の訪問と支出を調べる。少数の自己申告だけで地域全体の消費増を断定しない。

**完成の基準は「選んだ聖地と周辺地域スポットをつなぐコースの目安が分かり、各区間の実際の移動はGoogleマップで確かめられること」。**
